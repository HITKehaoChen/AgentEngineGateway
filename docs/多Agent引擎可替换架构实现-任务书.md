# 多 Agent 引擎可替换架构实现——任务书

## 1. 背景

Agent 网关 + Agent 引擎（Harness）的架构是当前 Agent 应用的主流架构之一。

例如：

- [OpenClaw](https://github.com/openclaw/openclaw)
- [内部 AI 应用员工助手](https://openx.huawei.com/myagent/overview)

都采用了类似的架构。

此架构下：

- **Agent 网关面向业务演进**，负责连接和映射具体业务到底层 Agent 引擎。
- **Agent 引擎面向智能执行能力演进**，负责完成实际任务。

以群助手业务为例：Agent 网关接受群助手请求后，需要将请求映射到底层引擎的一个具体 Session 进行处理，从而实现：

- 同一个群的会话连续性；
- 不同群会话之间的上下文隔离；
- 群助手权限限制。

业界 Agent 引擎百花齐放、竞争激烈，如 pi、OpenCode、Hermes、OpenDesk、DSH 等。Agent 应用架构设计需要考虑：如何在保持 Agent 应用架构稳定性的同时，快速接入业界先进的 Harness。

## 2. 任务描述

参赛者需要基于 Agent 网关 + Agent 引擎（Harness）的架构，构建一个支持多引擎快速切换的智能体系统。

参赛者可以基于任意技术栈实现，至少完成两种不同 Agent 引擎的接入。同时，参赛者需要实现赛题定义的 Agent 网关接口（见附件），用于评测。

## 3. 规则

### 3.1 技术方案要求

本比赛不限制参赛者所使用的技术方案。参赛者在满足基础要求的条件下，可以基于任意技术栈及现有代码实现。

#### 必须满足

- 代码支持在 Windows 系统运行，支撑评测；
- 可以通过环境变量改变引擎；
- 基础网关接口功能必须完成；
- 模型使用 GLM-5.2；
- 至少接入两种不同的 Agent 引擎。

#### 可选技术方案

1. 自行实现网关层代码，接入两种以上 Agent 引擎；
2. 基于赛题参考的员工助手内源代码，在项目已支持引擎的基础上，至少再支持一个引擎；
3. 基于开源代码构建，实现题目要求的网关层接口，并在项目已支持引擎的基础上，至少再支持一个引擎。

#### 可选不实现

为降低难度，以下要求可以不实现：

- 跨引擎的会话同步；
- 持久化存储，会话数据可以保存在内存中；
- 多 Agent 机制，可以在每个引擎内置一个默认 Agent，并基于该 Agent 创建会话。

### 3.2 评价规则

#### 客观评价指标（70%）

整体采用“Agent 执行 + LLM 裁判打分”的两阶段评测方法：

1. **Rollout（执行采集）**：让被测 Agent 在受控环境中执行任务，记录完整交互过程；
2. **Evaluation（裁判打分）**：由 LLM-as-Judge 评估 Agent 执行结果的质量。

#### 主观评价指标（30%）

- 方案、架构合理性：20%；
- 创新性：5%；
- 鲁棒性：5%。

#### 初赛得分计算

对选手引入的所有引擎分别执行一次评测；每个用例取各引擎得分中的最高分；所有评测用例得分之和为该题总分。

### 3.3 其他要求

1. 任何作弊嫌疑都将被要求提供解释；
2. 被证实作弊的选手将不被允许参与决赛评比；
3. 大赛组委会保留追溯权利，3 个月内被追溯并证实的作弊行为，其成绩将被取消。

> 选手需提交源码和编译启动方式，由赛题组在沙箱环境中完成评测。

## 4. 作品交付要求

### 4.1 目录结构

参赛作品打包为 `solution.zip`，解压后的目录结构如下：

```text
solution/
├── INSTRUCTION.md       # 裁判执行说明书（编译方式、执行步骤）
└── code/                # 完整源码（保持项目工程结构；如有 SDD 产物，也一并提交）
```

### 4.2 目录说明

#### `INSTRUCTION.md`

裁判执行说明书，用于指导自动评测系统部署、启动和执行参赛作品，并获取评测结果。至少包含：

- **环境准备**：依赖安装、服务启动；
- **执行方式**：启动命令、执行命令、参数说明、调用方式和执行顺序；
- **执行完成判定**：命令退出、服务返回完成状态或指定文件生成；
- **生成结果交付件说明**。

#### `code/`

完整源码，保持项目工程结构，并包含依赖声明和配置文件。

### 4.3 重要提示

- 缺少 `INSTRUCTION.md`，或 `INSTRUCTION.md` 无法指导自动执行，将导致作品无法完成自动评测；
- 执行过程如需人工交互，必须实现接口供裁判模型自动提交交互，否则将导致作品无法完成自动评测；
- 代码必须支持在 Windows 系统运行；
- 必须通过环境变量实现引擎切换；
- 基础网关接口功能必须完成；
- 至少接入两种不同的 Agent 引擎；
- 受限于判题资源，初赛阶段提交截止后统一进行一次评测；
- 选手需提交源码和编译启动方式，由赛题组在沙箱环境中完成评测。

## 5. 一页约束清单

| 维度 | 要求 |
| --- | --- |
| 架构 | Agent 网关 + 可替换 Agent 引擎（Harness） |
| 引擎数量 | 至少 2 种 |
| 引擎切换 | 必须通过环境变量实现 |
| 模型 | GLM-5.2 |
| 操作系统 | Windows |
| 网关接口 | 必须实现赛题附件定义的基础接口 |
| 会话同步 | 跨引擎同步可不实现 |
| 数据持久化 | 可不实现，可使用内存会话 |
| 多 Agent | 可不实现，每个引擎可内置一个默认 Agent |
| 客观评分 | 70%，Rollout + LLM-as-Judge |
| 主观评分 | 30%，架构 20% + 创新 5% + 鲁棒性 5% |
| 用例计分 | 同一用例取各引擎执行结果的最高分 |
| 交付格式 | `solution.zip`，包含 `INSTRUCTION.md` 与 `code/` |

## 6. 配套材料与当前缺口

### 6.1 已收录材料

- [Agent 网关接口规范](./Agent网关接口规范.md)：定义比赛评测所需的 HTTP API、会话状态、交互处理、SSE 事件流、错误处理和完整交互流程。

### 6.2 当前缺失材料

- 评测沙箱的具体环境与资源限制；
- GLM-5.2 的调用地址、鉴权方式及可用工具调用协议；
- 完整评测用例类别和结果提交协议。

这些材料会直接影响网关协议设计、引擎适配器接口以及自动评测执行链路，应在方案设计前补齐或显式建立假设。
