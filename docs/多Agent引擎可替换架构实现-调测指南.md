# 多 Agent 引擎可替换架构实现——调测指南

## 1. 环境准备

### 1.1 系统要求

- **操作系统**：Windows 10/11；
- **运行时环境**：根据所选技术栈安装对应运行环境，如 Node.js、Python 等；
- **模型服务**：需确保 GLM-5.2 模型服务可访问。

### 1.2 环境变量配置

通过环境变量切换引擎，示例：

```text
# 切换当前使用的 Agent 引擎
AGENT_ENGINE=opencode  # 或 pi、hermes 等
```

> 在 Windows CMD 中可使用 `set AGENT_ENGINE=opencode`；在 PowerShell 中可使用 `$env:AGENT_ENGINE = "opencode"`。最终使用方式以参赛作品的 `INSTRUCTION.md` 为准。

接口规范 v1.1 同时要求支持 `--engine` 启动参数。为兼容两份赛题材料，参赛作品应同时支持命令行参数和环境变量，建议采用以下解析优先级：

```text
--engine 命令行参数 > AGENT_ENGINE 环境变量 > 程序默认值
```

### 1.3 依赖安装

根据所选技术栈安装项目依赖，确保所有依赖包可正常下载。

## 2. 资源说明

### 2.1 评测数据集

评测用例为 JSON 格式，每条用例包含以下字段：

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| `task_id` | 任务唯一标识 | `office_002` |
| `title` | 任务标题 | 打开 Outlook 客户端 |
| `description` | 任务描述 | 自动打开 Outlook 邮件客户端 |
| `query` | 用户提问 | 请自动打开 Outlook 邮件客户端 |
| `category` | 任务分类 | 办公协作、沟通与日程管理类 |
| `secondary_category` | 二级分类 | 软件交互 |
| `difficulty` | 难度等级（数字） | `1` |
| `difficulty_label` | 难度标签 | 极易 |

### 2.2 模型资源

- **主模型（选手程序使用的模型）**：限定使用内部部署模型资源。可以参考[内部 Wiki：模型资源说明](https://wiki.huawei.com/domains/78815/wiki/236799/WIKI2026040710690580)中提供的模型。赛题组提供测试环境的 App ID 并协助申请资源，也可以使用其他内部部署的模型；
- **裁判模型**：用于 Evaluation 阶段的 LLM-as-Judge 打分。

> **待确认口径**：任务书明确要求“模型使用 GLM-5.2”，本指南的模型资源说明又提到“可以使用其他内部部署的模型”。在赛题组进一步确认前，方案实现应以 GLM-5.2 为默认且必测模型，不应仅依赖其他模型。

### 2.3 网关接口

参赛者需完整实现赛题定义的 [Agent 网关接口规范](./Agent网关接口规范.md)，包括会话管理、消息交互、交互处理、SSE 事件流和错误处理接口。

## 3. 调测步骤

### 3.1 第一步：环境验证

1. 确认运行环境安装正确，如 Node.js、Python 等；
2. 确认 GLM-5.2 模型服务可正常访问；
3. 确认环境变量配置生效。

### 3.2 第二步：单引擎调测

1. 启动网关服务，指定单一引擎，如 `AGENT_ENGINE=opencode`；
2. 发送简单评测用例，如 `difficulty=1` 的用例，验证基本流程：
   - 网关接收请求；
   - 映射到目标引擎；
   - 引擎执行任务；
   - 返回执行结果；
3. 检查返回结果是否符合预期；
4. 逐步测试不同难度的用例。

### 3.3 第三步：多引擎切换调测

1. 切换环境变量到另一个引擎，如 `AGENT_ENGINE=pi`；
2. 使用相同用例验证第二个引擎的执行流程；
3. 确认两个引擎均可正常工作；
4. 反复切换环境变量，验证引擎切换的稳定性。

Pi 运行前应确认 `pi --version` 为 `0.84.4`。Windows 下使用 `PI_COMMAND=pi`，Adapter 会直接执行项目锁定依赖中的 CLI JS；自定义命令只接受原生可执行文件或 `.js` 文件，不接受 `.cmd/.bat` shim。Pi Adapter 会为每个 Gateway Session 创建独立 RPC 进程，并在删除 Session 或退出网关时清理进程树。

### 3.4 第四步：评测流程验证

1. **Rollout 阶段验证**：让 Agent 在受控环境中执行任务，确认完整交互过程被正确记录；
2. **Evaluation 阶段验证**：使用 LLM-as-Judge 对执行结果进行打分，确认评分流程正常；
3. 检查评分结果是否合理。

### 3.5 第五步：全量用例测试

1. 运行全部评测用例；
2. 统计各引擎的得分情况；
3. 分析失败用例，定位问题原因。

## 4. 调测结果

### 4.1 结果分析

- 每个用例取多引擎中的最高分；
- 所有评测用例得分之和为该题总分；
- 关注客观指标（70%）和主观指标（30%）的综合表现。

### 4.2 验证方法

- 对比不同引擎在相同用例上的执行结果；
- 检查网关接口返回数据的完整性与正确性；
- 验证引擎切换后的会话隔离是否正常。

### 4.3 归档要求

- 提交完整源码；
- 提交编译启动方式说明；
- 由赛题组在沙箱环境完成评测。
